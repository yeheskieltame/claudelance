# v3.2 Design Spec - Batch `settleStake` to Cut Keeper Gas

Status: DESIGN ONLY. No Solidity change is made by this document. No mainnet
upgrade is proposed here - this is the spec the implementation + upgrade work
will follow once approved.

Target contract: `ClaudelanceCoreV3` (UUPS, EIP-7201 storage).
- Mainnet proxy `0x68c83D75Ee95860E83A893Aa13556AdE8411e3c8`, current impl
  `0x01A7Ee90F121Bd57BD1059f5B347C98e37aAaea7` (`version()` = `3.1.0`).
- Sepolia proxy `0x64b45Fe2C64951013389740AD530e5c664fd0Ffe`.

---

## 1. Problem: per-call `settleStake` gas

### How settlement works today

Stake settlement is a per-`(bounty, worker)` pull-pattern operation. The
on-chain entrypoint is:

```solidity
function settleStake(uint256 bountyId, address worker) external; // IClaudelanceCoreV3.sol:134
```

Implementation: `contracts/src/v3/ClaudelanceCoreV3.sol:382-413`. Per call it:

1. Loads `Bounty` + `Submission` storage (`_s()` EIP-7201 accessor).
2. Validates the bounty is `Resolved` or `Cancelled`
   (`BountyLib.validateSettleStake`, `contracts/src/v3/libraries/BountyLib.sol:109-114`).
3. Guards: `stakeRequired != 0` (`NoStakeRequired`), `hasClaimed[bountyId][worker]`
   (`NotClaimer`), and `!sub.stakeSettled` (`StakeAlreadySettled`)
   - errors defined in `contracts/src/v3/types/ClaudelanceTypes.sol:88,97,98`.
4. Sets `sub.stakeSettled = true` (idempotency flag, one SSTORE).
5. Decides forfeit vs refund and credits **either** `earnings[treasury][token]`
   **or** `earnings[worker][token]` (pull pattern - no outbound transfer).
6. Emits `StakeSettled(bountyId, worker, forfeited, stakeRequired)`
   (`IClaudelanceCoreV3.sol:47`).

The function is `nonReentrant` and permissionless ("Anyone (permissionless after
resolution): `settleStake(bountyId, worker)`", per `CLAUDE.md`).

### How the keeper calls it - the cost driver

The Railway relayer keeper (`apps/relayer/`, LIVE 2026-06-10) settles stakes
unattended every 5 min on mainnet v3. The planner emits **one action per
unsettled claimer**:

```ts
// apps/relayer/src/decisions.ts:46-49
for (const c of claimers) {
  if (!c.stakeSettled) actions.push({ kind: 'settleStake', bountyId, worker: c.worker });
}
```

The send loop then submits **one transaction per action, each consuming its own
nonce**:

```ts
// apps/relayer/src/keeper.ts:220-230 (abridged)
for (const { action, agentId } of ready) {
  const tx = action.kind === 'settleStake'
    ? await chain.settleStake(action.bountyId, action.worker, { nonce, gasPrice })
    : ...;
  nonce++;
  ...
}
```

`chain.settleStake` (`apps/relayer/src/chain.ts:347-349`) does a
simulate-then-send for each call. So a bounty that had **N** stakers who all
claimed produces **N separate on-chain transactions**, each paying:

- the 21,000 base tx cost,
- the keeper's per-tx overhead (signing, nonce, a separate `eth_call` simulation,
  a separate receipt wait),
- repeated calldata + warm/cold-access costs, even though `bounty` and `token`
  are the same across all N calls for one bounty.

Under direct-hire (`maxSlots = 1`) N is usually 1, so the win is small. But the
open `postBounty` path allows `MAX_SLOTS = 20` (`BountyLib.sol:33`), and any
open bounty with multiple claimers multiplies the keeper's fixed per-tx cost by
the number of claimers. The 21,000 base + simulation + receipt overhead is paid
N times instead of once. `pickWinner` is intentionally O(1) (it credits one
winner + treasury and returns), so settlement is the only fan-out cost on the
resolution tail, and it is borne entirely by the keeper wallet.

**Goal:** collapse the per-bounty fan-out into a single transaction so the
21,000 base cost + keeper per-tx overhead is amortized across all of a bounty's
stakers, while keeping the exact per-`(bounty, worker)` semantics and the O(1)
pull-pattern credit.

## 2. Proposed function

Add a batched settle path **alongside** the existing single-call `settleStake`
(do not remove or change `settleStake` - the SDK, frontend, and "permissionless
after resolution" guarantee all depend on it).

### Primary: `settleStakeMany` (single bounty, many workers)

This matches the keeper's actual access pattern: it plans per-bounty, then
fans out across that bounty's claimers (`decisions.ts:46-49`). One bounty's
`Bounty` storage + `token` are loaded once and reused for every worker.

```solidity
/// @notice Settle stakes for many workers of a single resolved/cancelled bounty.
/// @dev Permissionless, same semantics as settleStake per (bountyId, worker).
///      Skips (does not revert on) already-settled or non-claimer workers so a
///      keeper re-tick converges instead of reverting the whole batch.
function settleStakeMany(uint256 bountyId, address[] calldata workers) external;
```

Behavioral contract:
- Validate the bounty **once** (`validateSettleStake` - must be `Resolved` or
  `Cancelled`) and read `stakeRequired` / `token` / `winner` / `status` once.
- Revert once up front if `stakeRequired == 0` (`NoStakeRequired`) - a
  no-stake bounty has nothing to settle and the whole call is pointless.
- Loop `workers`. For each worker, run the **identical** per-worker logic as
  `settleStake`: skip (continue) if `!hasClaimed` or `sub.stakeSettled` already
  true, else set `stakeSettled`, compute forfeit/refund, credit
  `earnings[treasury|worker][token]`, emit `StakeSettled`.
- Per-worker **skip instead of revert** on the already-settled / not-a-claimer
  cases. Rationale: the single-call path reverts (`StakeAlreadySettled`,
  `NotClaimer`) and the keeper treats those reverts as benign convergence
  (`keeper.ts:259-262`). In a batch, one already-settled worker must not roll
  back the other workers' settlements, so the batch absorbs those cases
  internally and the keeper just sees fewer `StakeSettled` events.
- Keep `nonReentrant` on the external function (one guard for the whole batch;
  the credit step is pull-only so there is no reentrancy surface inside the
  loop regardless).

This is still **O(1) per `(bounty, worker)`** in the contract's own accounting
sense - each worker does the same fixed SSTORE/SLOAD work as the single call.
The batch only removes the *fixed per-transaction* overhead (base 21k,
calldata for repeated `bountyId`, signature, nonce, simulation, receipt) by
sharing it across the workers list. No new loops over unbounded protocol state
are introduced; the only loop is over the caller-supplied `workers` array.

### Optional secondary: `settleStakeBatch` (many bounties, paired workers)

A cross-bounty variant is **not** part of the recommended v3.2 scope. The keeper
plans per bounty and a per-bounty call already captures the dominant win
(re-using one `Bounty`/`token` load across that bounty's stakers). A
`settleStakeBatch(uint256[] bountyIds, address[] workers)` paired-array form
would re-load `Bounty` storage on every element (no shared-bounty saving) and
adds an array-length-mismatch failure mode, for a marginal extra saving of one
base-tx cost per bounty. Documented here only to record that it was considered
and deliberately deferred. If ever added, it must reuse the same per-element
skip-not-revert rule and enforce `bountyIds.length == workers.length`.

### Caller-side caps (off-chain, not a contract constant)

`MAX_SLOTS = 20` already bounds the number of claimers per open bounty
(`BountyLib.sol:33`), so `settleStakeMany`'s loop is naturally bounded at 20 for
any real bounty. The keeper should still chunk defensively (e.g. cap the
`workers` array length per call) so a single batch tx stays comfortably under
the block gas limit; this is a keeper config concern, not a new on-chain
constant, to avoid touching constants that the security review already cleared.

## 3. Storage safety (UUPS + EIP-7201)

**Conclusion: no storage layout change is required, and none is allowed.**

`settleStakeMany` is a **new external function only**. It introduces no new
state variables. It reads and writes exactly the same `CoreStorage` fields the
existing `settleStake` already touches:

- `bounties[bountyId]` (read)
- `submissions[bountyId][worker].stakeSettled` (read + write)
- `hasClaimed[bountyId][worker]` (read)
- `earnings[treasury][token]` / `earnings[worker][token]` (write)
- `totalProtocolRevenue[token]` (write, on forfeit)

All of these live in the single EIP-7201 namespaced struct `CoreStorage`
(`contracts/src/v3/storage/ClaudelanceStorageV3.sol:9-52`), reached through the
fixed slot:

```solidity
// ClaudelanceStorageV3.sol:60-61
bytes32 private constant _STORAGE_SLOT =
    0x7ab7ff2bfa5e2dd98317271785b381fe1fdd5645716d0d5e600e63a74bb79e00;
```

That slot is `keccak256(...claudelance.core.v3...) - 1 & ~0xff` per EIP-7201,
so the contract's entire mutable state is isolated in one namespaced region.
The file's own invariant is explicit:

> "Never change the order or type of existing fields - only append to
> CoreStorage." (`ClaudelanceStorageV3.sol:7`)

Because v3.2 adds **no** fields, there is nothing to append - the layout is
byte-for-byte identical to the live v3.1 impl. The single-slot namespace
guarantees that even if a future version *did* append, it could not collide
with OZ's `Initializable` / `Ownable2Step` / `Pausable` / `UUPS` slots (those
use their own ERC-7201 namespaces; v3 also keeps its reentrancy flag inside
`CoreStorage._locked` rather than OZ's, per the v3 base decision in `CLAUDE.md`).

### Layout-safety check (the gate)

Even though we are confident the layout is unchanged, the upgrade must prove it
mechanically before any Safe execution:

1. **OZ upgrade-safety validation.** Run the OpenZeppelin Upgrades storage-layout
   check (the same EIP-7201-aware comparison used since the v3 deploy) comparing
   the new v3.2 impl against the live v3.1 impl. Expected result: zero storage
   diffs, "compatible" verdict.
2. **`StorageLayout.t.sol`.** The architecture doc's test plan already names a
   slot-collision test across two impl versions
   (`docs/v3-contract-architecture.md`, `test/v3/StorageLayout.t.sol`). Extend it
   to assert v3.1 -> v3.2 produces no slot drift.
3. **`_STORAGE_SLOT` unchanged.** Assert the constant
   `0x7ab7...9e00` is identical in v3.2 (it is a `private constant`, so any
   accidental edit would surface in the diff and the test).

## 4. Upgrade plan (Safe-multisig-gated UUPS)

The v3 proxy upgrade authority is the Safe multisig
`0xe9Fc48f315fD4E989637fAcC29AaF2717E19f7F0` (threshold 2). The upgrade hook is
`_authorizeUpgrade(address) internal override onlyOwner {}`
(`docs/v3-contract-architecture.md` "UUPS upgrade gate"), and OZ v5's only
upgrade entrypoint is `upgradeToAndCall(address impl, bytes data)`
(`upgradeTo` was removed). So no single key can upgrade the contract.

### Sequence

1. **Implement** `settleStakeMany` in `ClaudelanceCoreV3.sol` (new external fn +
   the per-worker helper extracted from the existing `settleStake` body so both
   paths share identical logic and cannot drift). Bump `version()`
   (`ClaudelanceCoreV3.sol:653`) to `3.2.0`.
2. **Gate: security review.** Run `/security-review` + Slither on the diff. Per
   `CLAUDE.md` working conventions, every contract diff goes through
   `/security-review`, Slither, and the invariant suite before commit. v3.2 must
   clear with no Critical/High/Medium, matching the bar the original v3 deploy
   met (`docs/v3-contract-architecture.md` timeline: "Security review cleared
   (no Critical/High/Medium) - DONE").
3. **Gate: invariant + unit tests.** Run `forge test`, including
   `test/invariant/*` and the v3 suite. New tests required:
   - `settleStakeMany` credits each worker exactly as N single calls would
     (equivalence test: a batch over `[a,b,c]` leaves identical `earnings` and
     `totalProtocolRevenue` to three sequential `settleStake` calls).
   - Already-settled worker in the middle of the array is skipped, others still
     settle, no revert.
   - Non-claimer worker in the array is skipped.
   - `NoStakeRequired` reverts the whole call for a zero-stake bounty.
   - `StorageLayout.t.sol` v3.1 -> v3.2 zero-drift assertion (Section 3).
   - Invariant: `sum(earnings credited) + forfeits == sum(stakes pulled)` holds
     identically before and after, batched or not (no double-credit, no stake
     stranded). This protects the existing pull-pattern invariant.
4. **Stage on Sepolia.** Deploy the v3.2 impl to the Sepolia proxy
   `0x64b45Fe2C64951013389740AD530e5c664fd0Ffe`, run fork tests against live
   Sepolia, exercise the keeper against it with a multi-claimer bounty and
   confirm one tx settles all stakes.
5. **Mainnet upgrade via Safe.** Deploy the v3.2 impl with the Talent-registered
   deployer key (`--verify` against Celoscan), then execute
   `upgradeToAndCall(newImpl, "")` through the Safe UI
   (`https://app.safe.global`) with 2-of-N approval. `data` is empty - there is
   **no reinitializer** (no new state to initialize), so no `initializeV3_2` is
   needed; passing `""` to `upgradeToAndCall` is correct and avoids adding a
   reinit function that would itself need a guard.
6. **Post-upgrade verification.** Assert `version()` returns `3.2.0`, assert
   `getImplementation()` (SDK helper) points at the new impl, run a single
   `settleStakeMany` smoke settle on a resolved mainnet bounty's claimers.
7. **Keeper rollout.** Update `apps/relayer` to call `settleStakeMany` per
   bounty (replace the inner per-worker loop in `decisions.ts` / the dispatch in
   `keeper.ts:227-228` with one batched action that carries the `workers[]`).
   Keep the single-call path as a fallback for the chunk-tail / single-claimer
   case. Roll out dry-run-first, exactly as the original relayer rollout was
   (`CLAUDE.md` relayer row: "Rollout was dry-run-first").

### What does NOT change

- `settleStake(bountyId, worker)` stays, unchanged, permissionless. Public ABI is
  purely additive (new function, no signature changes), so `@yeheskieltame/
  claudelance-types` / `-sdk` get an additive bump, not a breaking one.
- No constant changes (`PROTOCOL_FEE_BPS`, `MAX_SLOTS`, `RESOLUTION_GRACE_PERIOD`
  all untouched).
- No change to `pickWinner` / `cancelExpired` / escrow math (`EscrowLib`).

## 5. Risks + gas-estimate rationale

### Gas rationale (qualitative)

- **Saved per batched bounty:** the fixed per-transaction cost paid once instead
  of N times - 21,000 base, one signature, one nonce, one simulation
  (`chain.simulateThenSend`), one receipt wait. For a bounty with N claimers the
  keeper goes from N txs to 1 tx, so roughly `(N-1) x 21,000` base gas plus
  `(N-1)` rounds of keeper/RPC overhead disappear. The `Bounty` + `token` SLOADs
  are warmed once and reused across the loop instead of being cold on every tx.
- **Not saved (and that is fine):** the genuinely per-worker work - the
  `stakeSettled` SSTORE, the `earnings[...]` SSTORE, the `StakeSettled` event -
  is identical in both paths because the semantics are identical per
  `(bounty, worker)`. Batching is a transaction-overhead optimization, not an
  accounting change.
- **Largest win** is on open bounties near `MAX_SLOTS` (up to 20 claimers).
  Under direct-hire (N=1) the batch costs the same as the single call (the loop
  runs once), so there is no regression on the dominant current path.

### Risks

| Risk | Mitigation |
|------|------------|
| Logic drift between `settleStake` and `settleStakeMany` | Extract the per-worker body into one internal helper both call; equivalence test in the suite (Section 4 gate 3). |
| One bad element reverting a whole batch (griefing / wasted gas) | Per-worker **skip-not-revert** for `!hasClaimed` / already-settled; only the up-front `NoStakeRequired` reverts the call. |
| Unbounded loop / block-gas-limit DoS | Loop is over caller-supplied `workers`, naturally bounded by `MAX_SLOTS = 20`; keeper additionally chunks. No loop over global protocol state. |
| Reentrancy via the loop | Pull pattern only - no outbound transfer inside settle; `nonReentrant` still wraps the whole batch. |
| Double-credit / stake stranded | Invariant test: total credited + forfeited == total staked, batched == sequential. |
| Storage collision on upgrade | None expected (no new state); proven by OZ layout check + `StorageLayout.t.sol` before Safe exec (Section 3). |
| Upgrade-key risk | `_authorizeUpgrade` is `onlyOwner` = Safe threshold-2; single-key compromise cannot ship the impl. |
| Empty `workers` array | Harmless - validates the bounty, loops zero times, emits nothing; cheap no-op. Optionally short-circuit. |

### Net

A purely additive, layout-safe UUPS upgrade that converts the keeper's
per-claimer settlement fan-out into one transaction per bounty, preserving the
exact pull-pattern semantics and gated behind the existing Safe-multisig +
security-review + invariant-test process. Expected impact scales with claimer
count; meaningful for multi-slot open bounties, neutral for direct-hire.
